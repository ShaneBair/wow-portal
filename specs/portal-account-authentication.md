# Portal Account Authentication

Status: Implemented locally with recommended defaults; deployment requires owner/operator verification  
Repository: `wow-portal`  
First consumer: `specs/player-boosts.md`

## Problem

The portal currently has no login or session concept. Registration, status, roster, and statistics are public to anyone who can reach the site. Player-specific tools such as boosts must know which AzerothCore account is making a request and must never trust an account or character identifier supplied by the browser without proving ownership.

## User Outcome

A player can sign in to the portal with the same account name and password used by the WotLK client. After login, the portal remembers the player for a bounded session, shows the signed-in account name, permits access to authenticated features, and provides an explicit Log out action.

The game account remains authoritative. The portal does not create a second password, copy plaintext credentials, or expose account IDs or password-verifier material to the browser.

## Current Behavior

- The React client has public Home and Stats routes and shared navigation.
- Express owns all API validation and secret-bearing integrations.
- `POST /api/register` uppercases account names and sends account creation through private AzerothCore SOAP.
- The portal already has a read-only MariaDB integration for statistics, but it has no authentication/session service.
- The browser has no protected routes, auth context, login page, or logout control.
- Express trusts one proxy hop. The actual production proxy topology and public origin have not been documented in this repository.

## Accepted Architecture

Authentication has three server-side parts:

1. Look up the canonical account name, salt, verifier, ban state, and 2FA presence through a dedicated least-privilege MariaDB account.
2. Reproduce AzerothCore's current `AccountMgr::CheckPassword` behavior locally: normalize the submitted password as AzerothCore does, calculate the SRP6 verifier using the stored salt, and compare it with the stored verifier in constant time.
3. On success, create a random opaque session ID stored only in an HTTP-only cookie. Keep session records in portal-process memory for this first version.

```text
Browser login form
      |
      | TLS + same-origin JSON
      v
Express authentication service
      |
      | parameterized SELECT only
      v
AzerothCore auth database
  account salt/verifier
```

Architectural rules:

- Do not send a player's password through a SOAP console command. Console command strings are not a suitable credential-verification protocol and may introduce command-injection or logging risk.
- Do not connect the browser to MariaDB, SOAP, authserver, or worldserver.
- Do not implement a synthetic login against authserver's game protocol. Portal authentication must not update AzerothCore session keys, last-login fields, failed-login counters, or IP-lock state.
- Do not reuse the SOAP service account as the player's identity. The SOAP account remains a privileged backend integration identity.
- Do not store a plaintext password, password-derived hash, salt, or verifier in a portal session, log, response, client cache, or portal-owned table.
- Existing Home, Stats, status, registration, roster, and statistics APIs remain public in this version. Only explicitly protected routes and APIs require a session.

## AzerothCore Compatibility Contract

AzerothCore is authoritative for password semantics. The compatible core currently:

- stores a random SRP6 salt and verifier for each account;
- uppercases the canonical account name and password with `Utf8ToUpperOnlyLatin` before registration/password checks;
- uses `Acore::Crypto::SRP6::CheckLogin` to validate a candidate password against the stored salt and verifier.

The portal implementation must be derived from and tested against the exact AzerothCore/Playerbots core revision deployed by the operator. Before enabling login, add non-secret test vectors generated by that compatible core covering:

- a correct password;
- an incorrect password;
- ASCII letter-case normalization;
- the exact byte order and fixed lengths of salt and verifier;
- the maximum account/password lengths supported by the deployed core.

Do not adopt a generic SRP package merely because it exposes similarly named parameters. AzerothCore's Grunt SRP6 representation and byte ordering must be proven compatible. Any future core change to password normalization, salt/verifier storage, or SRP parameters is an authentication integration change and requires updated fixtures before deployment.

## Account Eligibility

For version 1, an account may create a portal session only when all of these conditions are true:

- the canonical account exists;
- the password verifier matches;
- the account has no currently active account ban;
- the account does not have AzerothCore 2FA/TOTP configured.

Use the same public failure message for a missing account, wrong password, banned account, or 2FA-blocked account. This prevents the login API from becoming an account-discovery endpoint.

2FA-enabled accounts fail closed because verifying only their password would silently weaken their game-login policy. Supporting AzerothCore TOTP is a follow-up requiring a compatible secret-decryption and token-validation contract; the portal must not read the live authserver master key or ignore a populated `totp_secret` field.

IP and country locks remain game-login policies enforced by authserver. The portal must not guess their semantics from reverse-proxy IPs. Whether those locks should also govern portal access is an unresolved policy decision below.

## Input Normalization

The login form accepts:

- `username`: trimmed, then uppercased; 3-16 ASCII letters, digits, or underscores for version 1;
- `password`: 1-64 characters, with no NUL or line breaks, then normalized exactly as the compatible core before verifier calculation.

The wider password input bound permits older valid accounts without imposing the registration form's eight-character minimum. The compatible core remains authoritative; an overlong or otherwise incompatible password simply cannot verify.

Restricting usernames to the portal's existing ASCII registration contract is deliberate. Supporting legacy accounts with non-ASCII names requires a separately tested port of `Utf8ToUpperOnlyLatin` and is out of scope for this first version.

## Database Access

Introduce a dedicated portal-game database configuration rather than using the statistics reader implicitly:

```text
PORTAL_DB_HOST=
PORTAL_DB_PORT=3306
PORTAL_DB_USER=
PORTAL_DB_PASSWORD=
PORTAL_AUTH_DATABASE=
PORTAL_CHARACTERS_DATABASE=
PORTAL_STATE_DATABASE=
```

The final names may be adjusted during implementation, but authentication and boosts must share one documented, deliberately permissioned integration rather than reaching through the statistics service.

For authentication, the database user needs only the columns required to:

- select canonical username, numeric account ID, salt, verifier, and 2FA presence from the auth account table;
- determine whether that account has a currently active account ban.

`specs/player-boosts.md` adds narrowly scoped character reads and writes only to a portal-owned request table. This database user must not have `INSERT`, `UPDATE`, `DELETE`, `CREATE`, `ALTER`, or `DROP` rights on AzerothCore auth, characters, or world schemas.

Use validated database identifiers, parameterized values, a small pool, short query/connect timeouts, and a bounded queue. Creating the database user and grants is an explicit operator step. Portal startup must not grant itself permissions or mutate AzerothCore schemas.

If database configuration is absent or unavailable, public pages continue to work and login returns a generic temporary-unavailability response.

## Session Design

On successful login:

- generate at least 256 bits of cryptographically secure random session ID material;
- store only a one-way digest of the session ID in process memory;
- associate it with account ID, canonical account name, creation time, last-used time, absolute expiration, and a separate CSRF token digest;
- send the raw opaque session ID only in an HTTP-only cookie;
- rotate/replace any prior session cookie presented during login.

Proposed version 1 lifetime:

- 30-minute idle timeout;
- 8-hour absolute timeout;
- no sliding extension beyond the absolute timeout.

The cookie is:

- `HttpOnly`;
- `Secure` in production;
- `SameSite=Strict`;
- `Path=/`;
- emitted without a `Domain` attribute;
- preferably named with the `__Host-` prefix in HTTPS production.

Do not place the session ID in URLs, JSON bodies, JavaScript storage, or client-visible logs. Every authenticated response uses `Cache-Control: no-store`.

An in-memory session store is accepted because the portal currently runs as one process. A restart logs everyone out, which is safe and acceptable. Horizontal scaling, durable sessions, global revocation, and an account-facing session list require a shared session store and are out of scope.

## CSRF and Origin Protection

All mutating authentication and protected-feature requests must:

- be same-origin JSON requests;
- have an `Origin` header exactly matching a configured canonical public origin;
- reject missing, malformed, `null`, or mismatched origins in production;
- require the current session's CSRF token for authenticated mutations such as logout and boost submission.

Return the raw CSRF token only from the authenticated session endpoint. Keep it in React memory, not persistent browser storage, and send it in an `X-CSRF-Token` header. Compare token digests in constant time.

Add a documented local-development exception for HTTP and the development origin. Production must require TLS at the reverse proxy/tunnel and secure cookies. Verify `trust proxy` against the real topology before relying on `req.secure` or forwarded client addresses.

## HTTP API

### Log in

```text
POST /api/auth/login
Content-Type: application/json
```

Request:

```json
{
  "username": "SHANE",
  "password": "not-shown-here"
}
```

Success, HTTP `200`:

```json
{
  "authenticated": true,
  "account": {
    "username": "SHANE"
  },
  "csrfToken": "opaque-token"
}
```

Invalid credentials or ineligible account, HTTP `401`:

```json
{
  "error": "The account name or password is incorrect."
}
```

Dependency unavailable, HTTP `503`:

```json
{
  "error": "Login is temporarily unavailable."
}
```

### Read session

```text
GET /api/auth/session
```

Authenticated success, HTTP `200`, has the same public shape as login. Unauthenticated success is also HTTP `200`:

```json
{
  "authenticated": false
}
```

Expired, unknown, or malformed cookies are cleared and treated as unauthenticated. This endpoint never returns account ID, security level, email, salt, verifier, ban data, 2FA data, or session expiry internals.

### Log out

```text
POST /api/auth/logout
X-CSRF-Token: opaque-token
```

Authenticated success returns HTTP `204`, invalidates the server-side record, and expires the cookie. Logout is idempotent from the user's perspective; an absent/expired session may also return `204` after origin checks.

### Protected API behavior

Provide reusable server middleware that resolves a session and attaches an internal authenticated principal containing only account ID and canonical username. Protected APIs return:

- HTTP `401` with `{ "error": "Log in to continue." }` when no valid session exists;
- HTTP `403` with `{ "error": "This request could not be verified." }` for an invalid origin or CSRF token;
- no redirects from JSON APIs.

Do not accept account ID, username, or character ownership assertions from request headers or bodies as a substitute for the session principal.

## Abuse Protection

- Apply login limits by both effective client IP and normalized account name.
- Proposed starting limit: five failed attempts per account key and ten attempts per client IP in 15 minutes, with bounded in-memory state.
- Do not reset the account-key limit in a way that permits alternating valid and invalid attempts to bypass it.
- Perform a dummy compatible verifier calculation for syntactically valid unknown accounts so obvious timing differences do not reveal account existence.
- Add a small minimum response-time floor with jitter only if measurement shows a meaningful lookup/timing oracle; never use long sleeps that exhaust the server.
- Reject oversized bodies before parsing. The existing global `16kb` limit remains more than sufficient.
- Never log passwords, cookies, CSRF tokens, salts, verifiers, raw database rows, or complete login request bodies.
- Operational logs may contain a coarse result category, request correlation ID, and rate-limit key digest. Avoid logging a raw account name on failed login.

Authentication success must not bypass the separate rate, amount, ownership, and idempotency rules of an authenticated feature.

## React Experience

Add `/login` and auth state to the React application:

- The shared navigation adds `Boosts` as specified by `specs/player-boosts.md`.
- When signed out, show a `Log in` link or action in the shell.
- When signed in, show the canonical account name and a `Log out` button.
- `/login` has one page-level `h1`, labeled account/password inputs, a submit button, password-manager-compatible autocomplete attributes, visible focus, and an accessible error/status region.
- Never repopulate the password after a failed submission and clear component-held password state after success or unmount.
- A protected client route sends a signed-out user to `/login` with a validated same-origin return path. After successful login, return to that route.
- Only allow known internal return paths; never redirect to a caller-supplied absolute or protocol-relative URL.
- During initial session loading, show a neutral loading state rather than briefly rendering protected content.
- Client route protection is presentation only. Every protected API independently enforces the server session.

Express must serve the React entry document for direct requests to `/login` and `/boosts` in addition to the existing `/` and `/stats` allowlist. API and asset 404 behavior remains unchanged.

## Password and Session Privacy

- Require TLS for any non-loopback deployment before enabling login.
- Mark login/session/logout responses `Cache-Control: no-store` and avoid credential-bearing URLs.
- Set a restrictive referrer policy and retain the portal's no-third-party-runtime-assets posture.
- Browser errors are generic and never expose database names, SQL, verifier mismatches, ban status, 2FA presence, internal hosts, or stack traces.
- The portal must not claim that this session is a live game session; it is a separate portal session based on the same account credential.
- A game password change does not immediately revoke an existing in-memory portal session in version 1. The short lifetime bounds this exposure. Immediate password-change revocation is a documented follow-up.

## Configuration and Deployment

Document placeholder-only values in `.env.example` for:

- the dedicated portal database connection and validated schema identifiers;
- a canonical public origin;
- production cookie security mode if it cannot be derived safely;
- idle and absolute session durations only if operators need to tune them.

Do not add a separate session signing secret if opaque random sessions are stored server-side; the random ID itself is the bearer secret and only its digest is retained.

Deployment order:

1. Confirm the deployed compatible AzerothCore revision and generate verifier fixtures without using a real player's password.
2. Create the least-privilege database user and grants.
3. Configure the canonical HTTPS origin and verify proxy forwarding behavior.
4. Build and test the portal with mocked database rows.
5. Test with a dedicated non-privileged throwaway game account.
6. Enable authenticated features only after TLS, secure cookies, rate limits, and ownership checks are confirmed.

Do not print configuration values during startup or verification.

## Out of Scope

- Replacing AzerothCore's authentication protocol or password storage.
- Password reset, email verification, account recovery, or changing game passwords.
- Supporting AzerothCore TOTP in version 1.
- OAuth, social login, passkeys, or a separate portal identity.
- Role-based portal administration.
- Protecting existing public Home, registration, status, roster, or Stats behavior.
- Persistent sessions, multiple portal instances, device/session management, or “remember me.”
- Non-ASCII account names until exact core normalization is implemented and tested.

## Acceptance Criteria

- A valid eligible game account can log in and receives an opaque secure portal session.
- Wrong password, unknown account, active ban, and 2FA presence yield the same public `401` response.
- Password checking matches fixtures from the deployed compatible AzerothCore revision, including normalization and byte ordering.
- Passwords, salts, verifiers, cookies, and CSRF tokens appear in no browser response beyond the deliberately returned CSRF token, log, snapshot, or persistent portal table.
- Sessions expire after both the accepted idle and absolute bounds and are invalidated by logout.
- Secure, HTTP-only, host-only, same-site cookie behavior is verified behind the real HTTPS proxy.
- Protected APIs reject missing sessions and invalid origin/CSRF data even if the React route is bypassed.
- Login is rate-limited by both account and client IP without revealing account existence.
- Existing public routes and APIs continue to work when the account database is unavailable.
- Direct browser requests to `/login` and `/boosts` return the React entry document; missing assets and unknown APIs do not.
- `npm run build` and `npm test` pass without contacting live AzerothCore services.

## Automated Verification

Add focused server tests for:

- compatible SRP6 fixtures and incorrect-password cases;
- username/password validation and exact normalization;
- constant-length verifier handling and malformed database material;
- current, expired, banned, missing, and 2FA-enabled accounts;
- generic public failures and redacted logs;
- IP/account login rate limits;
- session creation, rotation, idle expiry, absolute expiry, lookup, and logout;
- secure cookie attributes in production and documented development behavior;
- origin and CSRF rejection;
- protected middleware principal behavior;
- database unavailable behavior without breaking public APIs.

Add frontend tests for:

- login success and error states;
- no password retention after success/unmount;
- initial session loading;
- signed-out protected-route redirection and safe return;
- signed-in account display and logout;
- no protected-content flash;
- keyboard and accessible-name behavior.

Use fabricated verifier fixtures and mocked database calls. Automated tests must not contain or submit a real password, contact the live database/authserver/worldserver, or create a game session.

## Operator Verification

1. Confirm the exact compatible core revision and compare portal verification against a dedicated test vector.
2. Inspect grants for the portal database user and prove it cannot modify AzerothCore tables.
3. Log in successfully with a dedicated ordinary test account.
4. Verify wrong, unknown, banned, and (if available) 2FA-enabled test accounts fail without distinguishable public details.
5. Inspect browser storage, cookies, responses, and server logs for credential leakage.
6. Verify cookie security and effective client IP behind the real tunnel/reverse proxy.
7. Exercise idle expiry, absolute expiry, logout, direct `/login`/`/boosts` refreshes, and an Express restart.
8. Confirm Home, registration, server status, roster, and Stats remain available while signed out.

## Unresolved Decisions for Owner Review

1. Confirm that accounts with AzerothCore TOTP should be blocked until full TOTP support exists. This is the recommended fail-closed behavior.
2. Confirm the proposed 30-minute idle and 8-hour absolute session lifetimes.
3. Decide whether AzerothCore account IP/country locks should affect portal eligibility. The recommended first version leaves them to authserver because proxy IP semantics differ.
4. Confirm that existing Home, Stats, roster, and registration features remain public while Boosts alone requires login.
5. Confirm whether the version 1 ASCII-only account-name constraint covers all accounts expected to use the portal.
